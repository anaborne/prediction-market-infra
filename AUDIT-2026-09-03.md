figure against the file it comes from, and every claim the prose makes about the code, and found
eleven issues. A second pass over the fixes found six more, so this file records seventeen items,
what was wrong in each, and what changed.

## 1. Matcher benchmark not reproducible run to run

Wrong: the corpus generator was seeded and the matcher's candidate selection was not. Seed tokens
were chosen with a stable sort over a `set`, so IDF ties broke on set iteration order, which
depends on CPython's per-process string hash randomization. Twelve runs of the documented command
put the score gate anywhere from 921 to 925, and the committed README block was one draw. The block
also omitted the `strong` line the script always prints, and labelled a wall time "median of 3"
while the documented command defaults to one repeat.

Changed: `_candidates` in `src/kalshi_bot/crossvenue/matching.py` sorts seed tokens on
`(-weight, token)` and ranks candidates on `(-score, market_id)`. Both orders are total, so no tie
falls through to iteration order. The README block was replaced with actual output, carries the
`strong` line, and no longer quotes a wall time.

## 2. `retention.py` docstring contradicts the retention table

Wrong: the module docstring gave `decision_results` 14 days and `market_snapshots` and
`index_observations` 7 days. The `_RETENTION` table twenty lines below reads 30, 14 and 14. Tests
pin the code's values, so the gate stayed green over a false docstring.

Changed: the docstring reads 30 days and 14 days.

## 3. Placeholder row in `parent_latency_summary.csv`

Wrong: the file ended with `wake_recv,,1,1.0000,1.0000,1.0000,1.0000`, which has an empty
`shadow_fire` flag, n=1 and four identical percentiles. Every other row carries a real flag and a
sample size between 734 and 1,115,945. The README and GUIDE §7.2 both cite the file as per-stage
evidence, and nothing in the repository reads or validates it.

Changed: the row was deleted.

## 4. Retention boundary test probes 7 days against a 14-day cutoff

Wrong: `test_boundary_row_exactly_at_the_cutoff_is_kept` inserted a row 7 days old and pruned it
against the 14-day `index_observations` cutoff, so the row was a week inside the window. The test
asserted a property it did not exercise and would have kept passing if `<` became `<=`.

Changed: the row is 14 days old, which is the cutoff. The test above it deletes rows at 15 days, so
both sides of the boundary are now covered.

## 5. Signing cost stated three incompatible ways

Wrong: GUIDE §7.2 said the isolated warm-loop signing microbenchmark "reads 1.65ms". That figure
appeared once in the repository with no source, and the five committed runs in
`benchmarks/history.csv` read p50 0.3303 to 0.9256ms. `docs/configuration.md` put the same quantity
at "~3 ms". ENGINEERING.md rule 6 is one number, one home.

Changed: GUIDE §7.2 attributes 1.65ms to the host it was measured on, states that the host's run is
not committed, and gives the committed range. `configuration.md` points at GUIDE §7.2 and carries
no figure of its own.

## 6. C++ comparison range understated as 2.4 to 5.0

Wrong: the README said executor-side `wake_recv` fell by a factor of 2.4 to 5.0. The six ratios
between rows 4 and 5 of `history.csv` are 4.92, 5.23 and 5.00 on asyncio and 2.81, 2.95 and 2.38 on
uvloop. p90 is a percentile the file carries.

Changed: "a factor of 2.4 to 5.2".

## 7. Dead anchor on the README link to GUIDE §4.2

Wrong: the fragment read `#42-cross-venue-arbitrage-kalshi--polymarket-us--does-not-exist`, with
two hyphens before `does`. GitHub's slugger strips the multiplication sign and the commas and
produces one hyphen there, so the link resolved to nothing.

Changed: the fragment matches the heading. Every relative link and anchor in the repository was
then checked, and all of them resolve.

## 8. `IPCPollerClient` documents full jitter, implements 0.5 to 1.5x

Wrong: the docstring said "exponential backoff + full jitter". The code sleeps
`backoff * (0.5 + random.random())`, which is uniform on 0.5 to 1.5 times the backoff. Full jitter
is `sleep(random.uniform(0, backoff))`, and with `_MAX_BACKOFF_S = 30.0` the implemented form waits
longer than the stated ceiling.

Changed: the docstring says exponential backoff with ±50% jitter and states where a single wait
lands.

## 9. `runtime/clock.py` points at a `docs/operations.md` that does not exist

Wrong: the docstring said "See `docs/operations.md`". `docs/` holds `GUIDE.md`,
`configuration.md`, `diagrams/` and `incidents/`. It was the only reference in the repository to a
documentation file that is not there.

Changed: the sentence says the parent system's soak procedure held the machine awake for this
reason, and that those operations notes are not part of this extraction.

## 10. README says CI runs on every push

Wrong: two sentences said CI runs on every push. `.github/workflows/ci.yml` triggers on pushes to
`main`, on pull requests, and on manual dispatch.

Changed: both sentences read "on every push to `main` and on every pull request".

## 11. `fees.py` calls all venues taker-only, then models a Kalshi maker fee

Wrong: the module docstring said the quadratic fee is "charged to takers only". Twenty lines below,
the same file maps `quadratic_with_maker_fees` to a maker multiplier of 1.0 and
`quadratic_with_combo_maker_fees` to 2.0, counts 130 and 3 live series against 13,265 plain
`quadratic`, and prices them through `TakerFeeModel.maker_fee_dollars()`. GUIDE §4 repeated the
claim as "Both are taker-only".

Changed: the `fees.py` docstring names the maker-fee case in the same sentence. GUIDE §4 says
Polymarket US is taker-only and Kalshi is taker-only except on the series whose `fee_type` carries
a maker multiplier.

## R2-1. Committed signing range stated as 0.33ms to 0.92ms

Wrong: the fix for issue 5 gave the committed range as p50 0.33ms to 0.92ms. The five
`sign_p50_ms` values are 0.3303, 0.3306, 0.3313, 0.9227 and 0.9256, and the largest rounds to 0.93,
so the stated range excluded its own maximum.

Changed: "0.33ms to 0.93ms".

## R2-2. `configuration.md` points at a section without the quantity it is about

Wrong: the sentence in `configuration.md` is about the cost of one signature on a shadow fire.
GUIDE §7.2 carried three signing figures, and none of them was that one. The quantity exists in the
repository, as the `sign,yes` row of `parent_latency_summary.csv`.

Changed: GUIDE §7.2 quotes that row at p50 5.50ms and p99 11.48ms on n=92,441, states that it sits
above the real-fire signature at both points, and cites the CSV as its home. The `configuration.md`
pointer is unchanged.

## R2-3. Incomplete account of what the README trims from the benchmark output

Wrong: the README said the run also prints a platform line and a wall time. It prints a platform
line, two wall times (one of them inside the `corpus:` line) and a three-line closing caveat.

Changed: "a platform line, two wall times and a closing caveat. Those are the host's or are
restated below, and are left out of this block."

## R2-4. The invariance claim on the benchmark block had no mechanism

Wrong: "Every count above is the same on any machine and in any process" was pinned by no test and
no CI step. The counts also ride on `math.log` in `crossvenue/text.py`, which is libm, so a
platform whose logarithm differs in the last bits could reorder IDF ties and move a market from one
verdict to another with every gate still green. ENGINEERING.md's own rule is that a guarantee
written only in prose decays silently, and this block had already drifted once.

Changed: `tests/crossvenue/test_bench_corpus.py` builds the same corpus at 800 × 300 markets with
40 planted pairs and pins the verdict counts and the narrowing counters, and asserts that the
`IDENTICAL` set is exactly the planted set. It runs in under a second. The suite went from 391
tests to 395, and the README badge and both inline counts were updated. The README now also says
which counts the test pins and which it does not.

## R2-5. The count 133 written in two files

Wrong: after the fix for issue 11, the count 133 appeared in both `crossvenue/fees.py` and GUIDE
§4, against ENGINEERING.md rule 6.

Changed: GUIDE §4 names the condition and points at `crossvenue/fees.py` for the census and the
count.

## R2-6. Backoff docstring says a wait "reaches" a bound it approaches

Wrong: the docstring said a single wait "reaches 45s". `random.random()` is strictly below 1.0, so
45s is a supremum that is never attained.

Changed: the docstring states the interval as [15s, 45s).

## What was checked and found correct

Environment: `uv sync --frozen --all-extras` on Linux x86_64, CPython 3.13.13.

`uv run pytest -q` reports 395 passed in 21.18s, with no skips and no xfails. The badge and both
inline counts in the README read 395, which is the number the suite reports. The suite was 391
before R2-4 added `tests/crossvenue/test_bench_corpus.py`.

`uv run mypy` reports success with no issues in 72 source files, under the repository's strict
configuration, over `src`, `tests` and `benchmarks`. `uv run ruff check .` passes and
`uv run ruff format --check .` reports 78 files already formatted. The gate list in
`.github/workflows/ci.yml` is the same list the README and ENGINEERING.md document.

The matcher's published counts reproduce under any hash seed. The documented command
(`cd benchmarks && uv run python matcher_bench.py`) was run nine times, once under the environment's
default hash randomization and once under each of `PYTHONHASHSEED` 0, 1, 2, 3, 7, 11, 42 and 99.
All nine runs printed the same counts, and all nine matched the README block: 531 tokens indexed,
25 dropped, 159,635 candidates scored, a 752x reduction, 924 cleared the score gate, 250 identical,
0 strong, 258 weak, 416 rejected, 250 of 250 planted pairs recovered, and 0 identical pairs that
were not planted. The arithmetic holds: 20,000 × 6,000 = 120,000,000, 120,000,000 / 159,635 =
751.7, and 250 + 0 + 258 + 416 = 924. `tests/crossvenue/test_bench_corpus.py` passed under
`PYTHONHASHSEED` 0, 1, 5, 13, 77 and 2026.

`benchmarks/latency_bench.py` and `benchmarks/orchestration/benchmark_flow.py` both ran end to end
with no credentials and no network. The flow's matcher task reproduced both committed rows of
`matcher_history.csv` exactly at the CI size: 4000 × 1500 markets, a reduction factor of 259,
23,135 candidates scored, and 100 of 100 planted pairs recovered.

Every figure the two rounds changed is written in one file. The retention periods live in
`retention.py`, the count 133 in `crossvenue/fees.py`, the backoff interval in `poller_client.py`,
the signing figures and the committed signing range in GUIDE §7.2, the C++ ratio range and the
matcher counts in the README, and the test count in the README alone. The parent system's
detect→fire percentiles are quoted in both the README and GUIDE §7.2, which predates this audit,
and every value quoted in either place matches `parent_latency_summary.csv` row for row.

The two CSV files the benchmarks append to were restored after the runs, and `git status` shows
only this file and `RECRUITER.md`.

## What remains unverifiable

Every figure that belongs to the parent system is outside this repository and cannot be checked
from a clone. That covers the whole-life detect→fire distribution on n=734 real order fires, the
shadow-fire distribution on n=92,441, every row of `benchmarks/parent_latency_summary.csv`, the
95,206 × 10,656 production scan and the 63,424 candidates it scored in 113 seconds, the results in
GUIDE §4 on calibration, parlay coherence and structural arbitrage, and the 4,233 rejections in
the 2026-08-22 incident. Checking any of them needs a live Kalshi demo account and the private
repository this code was extracted from. The C++ executor lives in a second repository that is not
present here, so the 2026-08-30 rows of `history.csv` that carry `cpp` in the `executor` column
were not reproduced either, and the confound the README states about them still stands. Absolute
latency is a property of the host, so the committed `history.csv` rows were measured on machines
this audit did not run on and were checked only for internal consistency and against the prose that
cites them. The matcher counts are independent of the machine and were the ones reproduced.
